Open-source MCP server · multi-repo AI context

Your codebase, indexed. Every AI tool, connected.

GPC shares project context across multiple Git repositories and serves bounded retrieval to Codex, Claude, Copilot and Gemini through one local MCP endpoint.

Chunks land in Postgres, vectors in Qdrant, embeddings from Ollama, and a consolidated Graphify knowledge graph in Neo4j. The canvas behind this text is the real graph of this repository — 1,365 nodes, 3,575 edges, 57 communities — not decoration.

Why it matters

AI coding tools stop relearning your codebase every session.

Most assistants forget the project the moment a chat ends. GPC keeps an indexed, retrievable view of your repositories outside the chat — so the next session starts with context, not silence.

Operator workflow

Verify, evaluate, package and audit context before trusting it.

GPC now includes a small operator surface around its retrieval-focused MCP server. Content and decision writes stay in CLI/indexer paths; MCP retrieval may record operational telemetry. Inspect the evidence before relying on local context.

Health

gpc verify + health-report

Check registry resolution, index state, services, Graphify visibility, staleness and drift in one operator report.

Freshness

gpc stale

Compare Git-visible relevant files against Postgres and Graphify so agents do not reason from stale context.

Quality

gpc eval-search

Compare semantic, lexical and hybrid retrieval on labeled queries. Inspect recall, MRR, nDCG and latency before making quality claims.

Handoff

gpc context-pack

Export a cited Markdown bundle with retrieved chunks, validation commands and token estimates for AI or human review.

Audit

gpc mcp-usage

Summarize MCP activity from Postgres with recursive redaction of secret-like fields.

Safety

maintenance doctor

Dry-run read-model diagnostics only. No reset, delete, table truncation or graph mutation.

Four stages, illustrated below. Indexing and embeddings stay local; retrieval searches the stored context, not arbitrary live files. Graphify remains a separate indexing workflow.

Context-engine evolution

Keep context fresh. Find the detail. Preserve the decision.

Three explicit, local workflows — not an autonomous agent or automatic chat memory. Implemented capabilities are separate from live validation and future work.

Implemented · opt-in

Watch the checkout you’re editing.

Start a foreground polling watcher for a registered repository. Debounce, retries and branch/worktree detection reconcile edits; shared local locks coordinate watcher, manual and hook indexing.

gpc watch .

No autostart, daemon or Graphify regeneration. This is the current checkout, not branch history; each linked worktree needs its own registered repo identity. Freshness depends on polling and indexing.

Watcher setup and limits ↗

Implemented · semantic default

Match meaning and exact identifiers.

Choose semantic, lexical (no embeddings) or hybrid rank fusion. Add repo filters and an explicit task: general, debug, implement, review or test. Results retain retrieval provenance.

gpc search 'index_project_path' \
  --project gpc --mode hybrid --task debug

gpc_search and gpc_context accept mode/task too. Identifier matching is textual, not an AST symbol index. Graph notes are independent post-retrieval annotations.

Retrieval modes and evaluation ↗

Implemented · explicit human review

Remember why, with evidence attached.

Capture a decision as pending, then approve it explicitly. Scope it to a project, repository and indexed source path. Evidence uses source content hashes to check freshness against the index — not to prove the live Git checkout is current.

Read-only MCP gpc_decisions returns approved, current decisions by default. Optional inactive diagnostics expose other states. Invalidation needs an actor and reason; supersession is explicit for the same key, not AI contradiction detection.

The actor is a local label, not an authenticated identity. No automatic conversation capture. Review and apply migration 0011 with gpc migrate before use; no hosted deployment is implied.

Graphify is a separate indexer that extracts the relationship graph of a repository — what calls what, what depends on what. GPC consolidates those graphs in Neo4j by project_slug and repo_slug, so a multi-repo product becomes one navigable system map.

Most AI tools read files. Graphify maps relationships. Together they answer questions like which worker calls which service or which modules touch the same database tables, instead of just returning matching text.

Frequently asked

Multi-repo AI context, MCP, local embeddings — answered.

Short answers to the questions developers ask most when evaluating GPC.

How do you share context between multiple Git repositories for AI coding tools?

Point GPC at each repository on your machine and it indexes them under a single project slug in Postgres + Qdrant. When any MCP-capable assistant — Codex, Claude, Copilot, Gemini — calls gpc.search, it receives bounded chunks from every repo that belongs to the project, plus the Graphify edges that connect them in Neo4j.

What is the Model Context Protocol (MCP) and how does GPC use it?

MCP is an open protocol for giving AI assistants access to external tools and data. GPC runs as a local MCP server that exposes tools like gpc.search, gpc.graph_neighbors and gpc.graph_path. Any MCP-aware client — Codex, Claude Code, Cursor, Continue — can connect and query the same indexed project.

Does GPC send my source code to any external service?

No. Indexing, embedding (via Ollama's nomic-embed-text) and retrieval all run on your machine. The AI coding tool that calls the MCP server still sends the retrieved chunks to its own model — but the choice of chunks, and the raw code, never leaves your box as part of the indexing pipeline.

How does GPC stay in sync with code changes?

Optional Git hooks trigger incremental indexing after commit, merge and checkout. For edits between Git commands, run gpc watch . in the foreground. It polls, debounces changes and retries failed or busy runs with shared local index locks. Healthy unchanged files avoid redundant embedding. It does not autostart or rebuild Graphify, and freshness depends on reconciliation completing. The index represents the current checkout, not every branch's history.

Can I search without embeddings or choose context for a task?

Semantic remains the default. Lexical mode uses Postgres for full-text, literal identifier and path matching without embeddings; hybrid combines lexical and semantic candidates using reciprocal rank fusion. CLI search and MCP gpc_search/gpc_context accept explicit mode, task and repository filters. Task preferences are lightweight heuristics, not a learned reranker. Compare a project-specific fixture before claiming a quality gain.

Does decision memory automatically learn from my conversations?

No. A human explicitly captures and approves a decision through the CLI. It is scoped to a project, repository and indexed path, with content-hash evidence. Current means current relative to the index, not proof of live Git freshness. Read-only gpc_decisions defaults to approved, current entries. Invalidation needs an actor and reason; same-key supersession is explicit. Actor labels are not authenticated identities.

How is GPC different from Copilot's workspace context or Cursor's indexing?

Those are tool-specific and scoped to the open workspace. GPC is tool-agnostic, runs outside the editor, and unifies context across many repositories under one project. It also exposes a structural graph (Graphify) that lets an AI answer questions no text search can — which worker calls which service, which modules share a database table.

What does the Graphify knowledge graph add on top of vector search?

Vector search returns text that looks similar to the query. Graphify models relationships — calls, contains, references, rationale_for — with EXTRACTED and INFERRED confidence tiers. gpc.graph_neighbors and gpc.graph_path let the AI traverse structure rather than just matching strings.

How many tokens does bounded retrieval actually save?

The bundled historical gpc token-savings sample records 25,737 indexed tokens versus 1,387 retrieved tokens — a 94.6% reduction for that example. This is not a benchmark of the current checkout or hybrid retrieval. Measure your own corpus and queries; fewer tokens alone do not establish answer correctness or total model cost.

What does installing and running GPC look like?

Clone the repo, run the installer (it brings up Postgres, Qdrant, Ollama and Neo4j via Docker), then gpc init in each repository you want indexed. The installer also wires the MCP config into Codex, Claude Code, Cursor and any other MCP client it detects.
